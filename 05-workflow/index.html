The failed charge is retried on its own, and the sleep lasts as long as you asked

Each step runs as its own invocation and its return value is recorded in the run's event log. When charge_card raises, the SDK runs it again about a second later. During workflow.sleep() no step and no workflow code is running: a delayed queue message wakes the run when the time is up.

For a step, started is when its first attempt began and finished is when the successful attempt ran. Both are read inside the step with workflow.get_step_metadata() and the system clock. The sleep's times are the events that began and ended it.

The workflow is plain async Python with two decorators

Excerpts from workflows.py and pyproject.toml. A step is a function the workflow can retry and record; the workflow body only orchestrates.

Every wake-up replays the workflow from the top, and finished steps don't run again

The run wakes up when it starts, when a step finishes and when the sleep ends. Each time, the body of process_order runs again from its first line. A step that already finished hands back the result stored in the event log instead of running. That is why the body has to be deterministic and reads the time with workflow.now() rather than the system clock.

What woke the run up, and what the replayed workflow body did each time
Woke up because At What the replayed body did
The run started … Reached reserve_inventory, which has no stored result, so it queued the step and stopped
reserve_inventory finished … Got the stored result of reserve_inventory without running it, then queued charge_card
charge_card finished … Got both stored results, read workflow.now() as the sleep start, recorded a 10 second sleep and stopped
The sleep ended … Got both stored results again, found the sleep complete, then queued send_receipt
send_receipt finished … Got all three stored results and returned them, so the run completed

Start a run to check this against real times. The result is built on the last wake-up, so if a step ran again on every replay its time in the result would be late. A stored result keeps the time of the step's only successful run.

The failed first attempt of charge_card is not a wake-up. A step that raises is retried by delivering its queue message again, about one second later by default and up to 3 retries, without replaying the body.

Vercel deploys the workflow as its own queue-triggered function

The project contains main.py, workflows.py, pyproject.toml and uv.lock. There is no vercel.json and no environment variable to set. One table in pyproject.toml adds the second function.

The path of your last run

  1. This browser

    Sends POST /api/runs, then GET /api/runs/{id} once a second until the run finishes.

  2. Web function

    Runs FastAPI in its region. workflow.start() records the run, queues it and answers in a few milliseconds.

  3. Vercel Queues

    Delivers one message per step, the retry of charge_card, and a delayed message that ends the sleep.

  4. Workflow function

    Replays process_order and runs each step as its own invocation, writing every result to the event log.

The region and edge location come from the x-vercel-id response header.

The Python SDK is in beta, and its API still changes between minor versions. A step's side effects repeat on every retry, so use get_step_metadata().step_id as an idempotency key. A sleep can last days; waits longer than 23 hours are chained. Run data is kept for 1 day after completion on Hobby, 7 on Pro and 30 on Enterprise, after which GET /api/runs/{run_id} returns 404. Run locally, the SDK keeps the queue in memory, so restarting the server during a sleep leaves the run stuck as running.
