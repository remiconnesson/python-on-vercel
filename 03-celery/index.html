The worker is a separate, private function

Both functions import tasks.py, which gives each instance a random ID when it starts. The web function puts its ID in every response, and the worker puts its own ID in the task's return value. Two different IDs mean the task ran outside the web function.

Each task is its own invocation of the worker

A classic celery worker runs tasks in a pool of processes that you size with --concurrency. Here there is no pool to size: each message is its own invocation of the worker function. Send five tasks back to back, without waiting for their results, and compare when each one ran.

What Vercel set up from this folder

The project contains main.py, tasks.py, worker.py, pyproject.toml and uv.lock. There is no vercel.json, no environment variable and no broker to provision; every decision below came from those files.

The path of the last task

  1. Web function

    POST /tasks enters at edge location … and calls add.delay(2, 3) on instance … in ….

  2. Vercel Queues

    Holds the message on topic celery-celery-on-vercel-celery, pinned to this deployment, and pushes it to the worker.

  3. Worker function

    Runs the task on instance … in …, one task per invocation.

  4. Runtime Cache

    Keeps the return value in the region until it expires or is evicted. GET /tasks/{id} on the web function reads it back.

Instance IDs and regions come from the last task's responses, and the edge location from their x-vercel-id header. Runtime Cache is regional, so the web function reads results stored in its own region.

There is no long-running worker process to keep alive

The task code is ordinary Celery. What changes is who runs it. Instead of a long-lived process that pulls from Redis or RabbitMQ, Vercel Queues invokes the worker function for each message, so no process sits polling a broker between tasks.

Endpoints and limits

Endpoints served by the web function
EndpointWhat it returns
GET /This page for browsers; the web function's instance, region and queue topic as JSON for everything else
POST /tasks?x=2&y=3Enqueues add(x, y) and returns the task ID, when it was published, and the web instance
GET /tasks/{task_id}The status read from Runtime Cache; on SUCCESS, the sum plus the worker's instance, region and timings

Runtime Cache is regional and can evict entries early, and Celery reads a missing result as PENDING, so treat results as short-lived status. Keep results you need in Redis or Postgres. Each task must finish within the function's maximum duration. Queues doesn't defer countdown or eta: the worker invocation holds the task until it is due, so keep delays short. Each message is consumed by the deployment that published it.
