A system binary from the image renders your text

figlet turns text into large letters made of ASCII characters. It is a Debian package, the kind of dependency a pip or uv install can’t add and the reason this app ships as a container. The Dockerfile installs it with apt-get, and GET /figlet runs it with subprocess.run on every request.

Fluid compute keeps the container running between requests

When the container starts, the app gives itself a random ID and notes the time. Fluid compute sends many requests to each running instance, so answers that carry the same ID and start time came from the same container and none of them waited for a cold start. Requests sent at the same time may be spread across more than one instance.

After 5 minutes without traffic in production, or 30 seconds in a preview, Vercel scales the instance in: it sends SIGTERM, allows 30 seconds to exit, and the next request starts a new container with a new ID.

What Vercel did with this folder

The folder holds a FastAPI app with a pyproject.toml, which on its own would select Vercel’s Python runtime. Dockerfile.vercel wins: Vercel checks for the Container preset before any other framework, and vercel.json pins it, so Vercel built the image instead.

  1. Detect

    Dockerfile.vercel at the root selects the Container preset, and vercel.json pins it with "framework": "container".

  2. Build

    The @vercel/container builder builds the image for linux/amd64 on each deployment, with this folder as the build context.

  3. Push

    The image is pushed to Vercel Container Registry, Vercel’s own image registry, tagged with the first 12 characters of the commit SHA.

  4. Serve

    One Vercel Function on Fluid compute receives every path and forwards it to the container on port 80, unless PORT is set.

Five details in Dockerfile.vercel that this depends on

FROM python:3.14-slim
COPY --from=ghcr.io/astral-sh/uv:0.12.23 /uv /bin/uv
RUN apt-get update \
    && apt-get install -y --no-install-recommends figlet \
    && rm -rf /var/lib/apt/lists/*
WORKDIR /app
ENV UV_COMPILE_BYTECODE=1
COPY pyproject.toml uv.lock ./
RUN uv sync --frozen --no-dev --no-cache
COPY main.py index.html ./
ENV PATH="/app/.venv/bin:$PATH" \
    PYTHONUNBUFFERED=1
CMD ["sh", "-c", "exec uvicorn main:app --host 0.0.0.0 --port ${PORT:-80}"]

The whole file with its comments removed.

apt-get install figlet
Adds a system binary to the image. The native Python runtime only installs Python packages.
uv sync --frozen
Installs exactly the versions pinned in uv.lock, without resolving them again.
--host 0.0.0.0
Vercel connects from outside the container. A server bound to 127.0.0.1 never sees the request.
--port ${PORT:-80}
Vercel sends traffic to port 80 unless PORT is set in the project settings.
exec
Replaces the shell with uvicorn, so uvicorn is process 1 and receives SIGTERM when the instance scales in.

It is a beta, with standard function limits and a few gaps

Container Images for Vercel Functions has been in beta on all plans since June 30, 2026. An image runs with the same limits and Active CPU pricing as any other Vercel Function, plus the constraints below.

Limits and gaps for container images on Vercel Functions
TopicWhat applies
Scale-inAfter 5 minutes idle in production, 30 seconds in a preview, with SIGTERM and a 30 second grace period
WorkloadsHTTP only: no background workers, no volumes and no persistent disk
NetworkingNo Secure Compute or Static IPs for container images yet
Duration300 seconds by default, up to 800 seconds on Pro and Enterprise
Memory and bodiesUp to 2 GB of memory on Hobby and 4 GB on Pro and Enterprise; request and response bodies up to 4.5 MB
Image size250 MB uncompressed for a standard function, up to 5 GB with Large Functions (beta); this image is about 200 MB
Image sourceBuilt from a Dockerfile or pushed to Vercel Container Registry; not pulled from Docker Hub, GHCR or ECR
